# AGENTS.md

This file provides guidance to coding agents (Claude Code, OpenCode) when working with code in this repository.

## Project Overview

A single dependency-free TypeScript file that drafts Tempo Timesheets worklogs (Jira Cloud) from GitHub commits and pull request reviews, a calendar and Jira activity, and books approved lines through the Tempo REST API v4. Node.js runs it directly (versions in `engines` of `package.json`); there are no dependencies and no build. Unit tests in `tempo_timesheet_drafter.test.ts` use `node:test`. `package.json` points `node .` to the file (`main`), declares ES modules and the `test` script. The repository is also an agent skill (`SKILL.md`).

## Common Commands

```sh
node --run test                         # unit tests, no network, no .env
node .                                  # help, doubles as a syntax check
node . demo                             # all views with made-up data, no API calls
node . draft 2026-11-02..2026-11-04     # read-only
node . book --dry-run draft.txt         # read-only: checks lines, shows what would be booked
node . book draft.txt                   # writes worklogs to Tempo
```

The README image needs [freeze](https://github.com/charmbracelet/freeze); `docs/images/terminal.ts` fakes a 100-column terminal on the demo's Tuesday at 13:40. Render it again after a change to the grid:

```sh
node --import ./docs/images/terminal.ts . demo --grid | freeze --language ansi --window --background "#0C0C0C" --padding 30 --margin 0 --font.size 14 --line-height 1.4 --output docs/images/demo.svg
```

Run `node --run test` after every change; try API behavior with `draft` and `book --dry-run` only. Run `book` only with lines the user approved; it creates real worklogs.

## Configuration

All configuration lives in `.env` next to the program (gitignored), loaded with `process.loadEnvFile`. Variables already set in the environment win. The variables are documented only in `README.md`; keep that the single source. Never read, print or commit `.env`.

## Architecture

- **Budget:** Tempo `/4/user-schedule` (required seconds and holidays of the token owner) minus `/4/worklogs/user/{accountId}`. The account id comes from Jira `/rest/api/3/myself`.
- **Channels:** GitHub (GraphQL: repositories of `GITHUB_OWNERS` pushed since the start date, their branches with the last commit's date, then the history of each branch committed to since the start date, filtered by the viewer as author; `pullRequests`: per owner a search `reviewed-by:@me` with the viewer's last reviews and their inline comments, and `viewer.issueComments` newest first for conversation comments), calendar (`CALENDAR_ICS_URL`, parsed in-house), Jira (`updatedBy(accountId, from, to)` with comments in one search, then `/rest/api/3/changelog/bulkfetch`; creations, comments and changes by the account; `lastViews`: JQL `lastViewed` in the range, one `View` per issue with its summary). GitHub and Jira changes yield timed `Activity` records. GitHub and the calendar need nothing from Jira and start with the first requests; commits and pull request events wait for the project keys only to be matched to issues (`commitActivities`, `pullRequestActivities`).
- **Planning (`planDay`):** meetings at their time; each free quarter-hour goes to the issue with the highest `WEIGHT` sum of its activity; a gap of up to `MAX_GAP` before an owned quarter-hour goes to that issue. Then views: a quarter-hour still free goes to the issue last viewed in it, and the free quarter-hours after a quarter-hour whose owner was viewed in it, up to `MAX_GAP`, go to that issue too; a view in the last `MEETING_TAIL` minutes of a meeting counts for the next quarter-hour, a view during a worklog on the same issue fills from the worklog's end, and `BATCH_SIZE` issues viewed within `ACTION_MS` do not count. Longer gaps stay open and are listed.
- **Output (`draft`):** per day a header with booked plus drafted against required hours, the lines in time order (draft and booked `#  ✓`, each date under the header's weekday), then `#  ?` questions, `#  !` missing hours and `#  ·` sources, each mark under the `✓` (`calendar:` meetings by time and key, `viewed:` quarter-hours filled by views, `<ISSUE-KEY>:` commit subjects or pull requests behind `Implementation`/`Review`). Entry lines carry no trailing comment, so what the user approves is what `book` reads. `show` picks the view: the week grid (`printGrid`) at a terminal, its rule under each day filled toward the required hours like the list's header (`filledCells`) and the entry running now in orange, the list (`printDraft`, colored and wrapped only at a terminal) with `--list` or whenever stdout is not a terminal. While fetching, `progress` draws one line on stderr (`statusLine`) and leaves one summary line (`summaryLine`).
- **Command line (`main`):** help on no command, `help`, `-h` or `--help` (stdout, exit 0, no network); usage errors as `UsageError` on stderr with the relevant usage line and a "did you mean" from `closest`, exit 2; other failures exit 1. Ranges are validated and missing variables listed together before the first request.
- **Booking (`book`):** two phases. `check` validates every line (format, real date and time, not in the future, issue key to id via Jira), then classifies it against existing worklogs and earlier lines (duplicate, repeat, overlap); any problem aborts before the first `POST`. Then `POST /4/worklogs` per line and day totals against `/4/user-schedule`. `--dry-run` stops after the classification.

## Non-obvious behavior

- **Planning rules are measured, not guessed.** `tempo_timesheet_drafter.fixture.json` holds the facts of real days (renamed keys, placeholder texts; dates, times and changed field names kept), the worklogs booked on them and the suggestions Tempo showed for 2026-11-02..05. It shows real working hours, so it stays local: `.gitignore` lists it, and without it the last test is skipped. The last test scores `planDay` per quarter-hour against them with exact counts, so every rule change shows its effect. Days booked by hand are the reference that counts; days booked from this tool's draft agree with it by construction and are scored apart (`byTool`); Tempo's suggestions only decide between variants. A rule change must not lower `bookedByHand.same`; a drop of `bookedByTool.same` is reported and its expected counts updated, since any new source moves lines on a day booked from the old draft. The fixture's views cannot be fetched again (Jira keeps only the latest), so the fixture is extended, never recaptured: new records are appended, with the rename map of the first capture so existing keys keep their names.
- **`main()` runs only under `import.meta.main`**, so the tests import the functions without running the program. Comparing `process.argv[1]` does not work: `node .` passes the directory. `import.meta.main` exists from Node.js 24.2 (stability 1.0, experimental).
- **GitHub's `history(since:)` filters by committer date, the day is the authored date.** A rebased commit is authored on one day and committed later, so the query starts at the range's start and has no `until`; the authored date is filtered afterwards. Commit search (`search/commits`) only indexes default branches and is unusable here.
- **Only branches committed to since the start date are read.** Reading every branch's history took 9 requests in a row for a repository with 407 branches, the whole run's time, and more workers do not shorten one repository's chain. Listing the branches with their last commit's date takes 100 per request; a branch whose last commit is older than the start date holds no newer commit (a parent is committed before its children, except with a wrong clock, and a rebase sets a new committer date), so only the rest is read, 50 branches per request as aliases.
- **Required hours never cap the draft.** Every day in the range is planned, also one booked to its required hours, a weekend or a holiday: a full day can still hold unbooked work, and stopping there hid it. The required hours only feed the header and the `!` note.
- **Gaps are intentional.** The draft never fills a day to the required hours: a long gap without activity may be a break or an absence, so only gaps up to `MAX_GAP` are attributed, to the issue whose activity ends them (work leads up to the commit or change that records it).
- **One action counts once.** Jira records one action as several changes seconds apart (creation, attachment and priority; description and status), so Jira changes to one issue within `ACTION_MS` of the first change counted count once. Ties in a quarter-hour go to the later minute, then to the earlier change within it (Tempo's choice on the fixture), then to the issue key: never to the order in which parallel requests finished.
- **Batch changes count once (`collapseBatches`).** The same changed fields on `BATCH_SIZE` or more issues, each within a minute of the previous, is one action such as closing an epic list; counted per issue, it would hand the quarter-hour to an arbitrary one. It counts for the common parent (an issue's family is its parent, or itself without one), otherwise for one of its issues, like Tempo: the one viewed first within `ACTION_MS` of the batch, else the one changed first; the `· batch:` note lists the others. Tempo picked another member on the fixture's one batch (no rule from one sample reproduces it); the booked days gain a quarter-hour.
- **Merges:** a `Merge pull request` merge is a review of the issue in its branch name; other merges (`Merge develop into issue/X`) count as activity only with an issue key and are skipped otherwise. The kind `review` stays the merge commit; the viewer's own reviews and comments are `pr-review` and `pr-comment`, so an approval followed by the merge counts both.
- **Pull request comments count when written, reviews when submitted.** An inline comment's `createdAt` (equal to `draftedAt`) is when it was typed into the pending review, minutes before the review's `submittedAt`; the review's `publishedAt` is when it was started, not submitted. A reply in a thread outside a pending review is its own `COMMENTED` review without body, so such reviews count only through their comment. `PENDING` reviews and comments are left out. Comments on the viewer's own pull request (`own`) are `Implementation`: answering reviewers is part of the work. Measured on the fixture (55 events on 14 days): a comment weighs like a commit, a review like a Jira change; the hand-booked days gain 3 quarter-hours, the weights 1–3 differ by at most one, filling only free quarter-hours gains 2.
- **Why a search per owner, not `contributionsCollection`.** `pullRequestReviewContributions` returns only the latest review per pull request and needs `read:user` for private repositories; GitHub has no connection of a user's review comments. `reviewed-by:@me` also finds pull requests with only thread replies, including the viewer's own (checked live; `commenter:@me` found the same set). The search starts `SEARCH_LEAD_DAYS` before the range because its index can lag behind a pull request's `updatedAt`, and a closed `updated:` range would miss pull requests updated again later; reviews and comments are filtered by time afterwards. `reviews` lists oldest first, so `last:` reads the newest. GitHub's GraphQL API signals rate limits with 200 or 403, never 429, and a query of more than 10 s answers 502 (not retried for `POST`), hence pages of 25. Errors beside data (a repository the token may not read) become warnings, and a failed request skips only its part, so pull requests never stop a draft.
- **Jira changelog timestamps:** `changelog/bulkfetch` returns `created` as epoch milliseconds, the search returns ISO strings; both go through `new Date`. Tempo's own activity suggestions are not available through its public API, so this is a rebuild from Jira data.
- **Views come from Jira's last view per issue.** Tempo's suggestions are mostly issue views. Atlassian keeps only the latest view per issue (JQL `lastViewed`), server-side and from any device; a browser history would see only the computer it lies on. A later view replaces the earlier one, so views serve drafting recent days; on the fixture's hand-booked days (four weeks old) they change nothing, on Tempo's days they add 8 quarter-hours. A search is not a view, and `GET /issue` counts only with `updateHistory=true`, so drafting and `book` do not move it. Views fill only what activity left open: as a weight they would move lines that commits and changes place.
- **Tempo's own suggestions are not read.** Tempo has no public API for them; only documented endpoints are used. Revisit when Tempo publishes a suggestions endpoint.
- **Issue keys are validated against the Jira project list**, so `UTF-8` or `ISO-8601` never become issues. Keys may contain digits and underscores (`C3-12`, `T3D-1`).
- **`book` is all or nothing for line errors, not for overlaps.** A wrong line left among booked ones would be easy to miss, so one problem stops all posting. Overlaps only warn: the draft itself places overlapping meetings (marked `overlaps`), and Tempo accepts them.
- **Who gets which output.** Agents read 2D layouts poorly and pay for every escape code, and recent Claude Code runs commands in a PTY, so `isTTY` alone does not tell: `AI_AGENT`, `OPENCODE`, `CLAUDECODE` and `CODEX_*` also mean plain output, as do `TERM=dumb` and a redirect. A redirect always gets the plain list, even with `FORCE_COLOR` or `--grid`, so `draft > draft.txt` is a file `book` reads; `book` also strips escape codes in case colored lines are copied in. `NO_COLOR` drops colors but keeps bold.
- **Issue keys link wherever colors are shown (OSC 8, `hyperlinks`), with no list of known terminals.** Windows Terminal sets no `WT_SESSION` when it takes over a shell as the default terminal (microsoft/terminal#13006), so a `WT_SESSION` check (as in `supports-hyperlinks`) left the links out there; conhost and terminals without OSC 8 show the plain key. Only a missing `ATLASSIAN_SITE`, `FORCE_HYPERLINK=0`, `Apple_Terminal` and `demo` (made-up keys) turn them off. Keys in notes link only for Jira projects or issues of the shown lines, so `UTF-8` stays text; the link covers the key, never its padding.
- **No progress bar.** Fixed shares per source were guesses: the fast sources filled half the bar in a second and GitHub crawled through the rest. The line shows only what is known: `✓`/`✗` per source, `…` while it runs (GitHub too: a repository count beside the others' `…` looked like the only source making progress; its total and skipped repositories go into the summary) and, from 3 seconds, how long a running source has taken (Bazel's threshold, so a hang shows while the spinner keeps turning). It appears after 500 ms (cargo), so short runs do not flicker, and stays below the last column, since a full row wraps on Windows Terminal and breaks the `\r` redraw; finished sources leave first when it is too narrow. One summary line stays on stderr, also after a failure so the `✗` is still visible above the error; like the live line it stays below the last column (too wide, each source keeps its first count, then only its name). Blank lines set the live line and the summary apart from the command and the draft; after a failure, `main`'s blank line before the error is the one below. Like the live line, it is for a person at a terminal only: agents read the sources from the draft.
- **The entry running now is orange, not underlined.** The now line used to continue over blocks as a colored underline (`4;58;2;r;g;b`). Windows Terminal reads SGR 58 only in the colon form (`58:2::r:g:b`, microsoft/terminal#15795) and took the semicolon form's numbers as separate attributes, which dropped the row's background; a thin underline was also hard to see on a block. The line stays in free cells.
- **Wrapped list lines continue without `#`.** A copied continuation then fails loudly in `book` instead of booking a shortened description; `#` lines continue as comments.
- **The description runs to the end of the line.** A ` # ` used to start a trailing comment, which cut Jira summaries and meeting titles containing `#`.
- **Every `POST` sends `remainingEstimateSeconds`.** Some projects reject worklogs without it ("Geschätzte Restzeit des Vorgangs darf nicht leer sein"). The value is the issue's remaining estimate from `check` minus the time spent, not below 0, like Jira's auto-adjust. Within a run, the reduced value carries over to the issue's next line.
- **No retry of `POST` after a 5xx.** The worklog may exist already; rerunning `book` is safe because of the duplicate check. 429 is retried at most three times after at least one second (Tempo's limit is 5 requests per second per IP).
- **Calendar parsing:** lines are unfolded on bytes because a fold may split a UTF-8 character. Occurrences are expanded in the event's wall time and then converted: Windows zone names (Outlook) through the feed's `VTIMEZONE` transitions, IANA names through `Intl`, floating times as local. `EXDATE` and `RECURRENCE-ID` match occurrences by converted local minute; a date-only `EXDATE` drops the whole day. Outlook does not always set `STATUS:CANCELLED`, hence the `Canceled:`/`Abgesagt:` prefix check, and published Outlook feeds no longer carry attendees, so declined meetings are detected only where `PARTSTAT` exists. `BYSETPOS` with several `BYDAY` values and `RANGE=THISANDFUTURE` are not supported.
- **Scoped Atlassian tokens do not work with the site URL**; the README asks for a token without scopes so one token covers Jira on `ATLASSIAN_SITE`.

## Code Comments

Comments explain **why**, not **what**. Default to no comment; prefer a clearer name. Document a non-obvious decision once, here under "Non-obvious behavior", and keep code comments terse. History lives in git, not in comments.

## Scratch Files

Non-committed agent artifacts (test harnesses, sample calendars, drafts) go under `.tmp/sessions/<session-id>/` at the repo root; `.tmp/` is gitignored. Never write scratch files to the repo root.
